§1 (the problem): a numerical program is mostly bookkeeping — collections of numbers, lookups, grouping, filtering, reading a file of measurements — and the choice of container decides whether the program is clear and fast or a mess of index arithmetic that runs in O(n²). The forcing problem: you have ten thousand measurements keyed by sensor name and need per-sensor summaries; nested lists and linear search make this painful, and a dict makes it a three-line loop. §2 (the intuition): a list is a growable array of references (so indexing is O(1) and inserting at the front is O(n)); a dict is a hash table — the hash of the key tells you where to look, which is why lookup is O(1) and why keys must be immutable; a set is a dict without values; an iterator is a thing that hands you the next item on demand, so a generator can produce a billion items without storing them.

Topics in order: lists — construction, indexing and slicing (negative indices, strides, slice assignment), `append`/`extend`/`insert`/`pop`/`remove`/`index`/`count`/`sort`/`reverse`, `sorted` vs `.sort()`, `key=` functions and `reverse=`, stability, sorting by multiple keys with tuples, big-O of each operation and why (the growable-array picture; `collections.deque` for O(1) at both ends); tuples — immutability, packing/unpacking, swap idiom, star-unpacking, `namedtuple`; the copy problem — shallow vs deep (`copy.copy`, `copy.deepcopy`, `list(a)`, `a[:]`), nested lists and the `[[0]*n]*m` trap; dicts — construction, lookup, `get` with default, `setdefault`, `defaultdict`, `Counter`, iteration over keys/values/items, insertion order guarantee (3.7+), dict comprehensions, merging (`|`), hashability and why lists cannot be keys; sets — membership, union/intersection/difference, set comprehensions, frozenset; the hashing story in plain words (hash → bucket → equality check; collisions; why `hash(1) == hash(1.0)`); comprehensions (list, dict, set, nested, with conditions) and when a plain loop is clearer; iteration protocol — `iter`, `next`, `StopIteration`, `for` desugared into a `while` with `try`; generators — `yield`, laziness, generator expressions, infinite generators, `itertools` (count, islice, chain, product, combinations, groupby, accumulate), `enumerate`, `zip` (strict=True), `reversed`, `any`/`all`, `sum`/`min`/`max` with keys; strings revisited — `split`/`join`, `str.translate`, `in`, `str` vs `bytes` and encodings in one paragraph; files — `open` with `with`, text vs binary mode, reading lazily line by line, `pathlib.Path` (exists, glob, read_text, write_text, parents), CSV via the `csv` module (reader, DictReader, writer), JSON via `json` (dump/load, what maps to what, floats and `nan`); a closing section "choosing a container" as a decision table (need order? duplicates? lookup by key? both ends?).

Build-it-yourself sequences: (1) a singly linked list class-free (nested tuples) and then as nested dicts, to feel why insertion at the front is cheap there and expensive for a list; (2) measure list-`in` vs set-`in` timing for n = 10³…10⁶ with `time.perf_counter` and read off O(n) vs O(1) (project plots it); (3) write `my_enumerate`, `my_zip`, `my_range` as generators and show they match the built-ins; (4) implement word-frequency counting three ways — nested loops with lists, dict with `get`, `Counter` — and compare line counts and timings; (5) a sparse polynomial as a dict {power: coefficient} with add/multiply/evaluate/derivative, checked against `numpy.polynomial` in the project; (6) desugar a `for` loop into the iterator protocol by hand.

Worked examples (≥6): slicing diagrams with negative strides and the "reverse a string" idiom; the `[[0]*3]*3` trap diagrammed and fixed with a comprehension; sorting a list of (name, score) records by score descending then name; `groupby` on sorted records vs a `defaultdict(list)` solution; a generator pipeline that reads a 10⁶-line file, filters, and sums without ever holding the file in memory; JSON round-trip of a nested dict with a float that prints differently.

Project (standard library; numpy only for the final cross-check): generate a synthetic sensor log (10⁵ lines: timestamp, sensor name, reading) with `random` seeded; parse it with a generator pipeline; per-sensor count/mean/min/max with `defaultdict`, asserted against a second independent computation (sorted + groupby); the list-vs-set membership timing experiment with a log-log plot and a fitted slope asserted near 1 for list and near 0 for set; the sparse-polynomial dict module with `__main__` tests asserted against `numpy.polynomial.Polynomial`; CSV and JSON writers for the summaries and a round-trip assert; a deep-copy vs shallow-copy demonstration asserted. "Your turn": a `Counter`-based anagram grouper; `itertools.product` to enumerate a parameter grid lazily; rewrite one nested-loop solution as a comprehension and one comprehension back into a loop, and say which is clearer.

§8 honest: slicing is half-open and negative strides reverse the direction of *both* endpoints — everyone gets `s[5:2:-1]` wrong once; `sort()` returns `None` and people write `a = a.sort()`; shallow copy of nested structures is the bug that costs a day; dict iteration order being insertion order is guaranteed only since 3.7, and relying on it in `set` is a bug (sets are unordered); generators are consumed once — iterating twice silently yields nothing the second time; `zip` truncates silently unless `strict=True`; comprehension nesting order reads left to right like the loops, which no one believes until they test it.
