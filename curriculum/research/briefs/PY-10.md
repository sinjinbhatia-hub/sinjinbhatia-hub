Read the PY addendum in research/WRITER-BRIEF.md first.

§1 (the problem): a direct N-body gravitational simulation (CM-5 forces, N = 500, 2000 steps) in pure Python takes an hour; the same physics vectorized takes seconds, and over many initial conditions it parallelizes across cores. But most students optimize the wrong thing first because they guess instead of measuring, and most student code cannot be re-run by anyone — including its author — six months later. The forcing problem is twofold: make the simulation fast by measurement, and make it a piece of software (a package with tests, a CLI, and a reproducible environment) rather than a script. §2 (the intuition): Python is slow per operation because every `a + b` is a dynamic dispatch on boxed objects; the fast path is to push loops into compiled code (NumPy, Numba) or to run many Python processes at once (multiprocessing — the GIL means threads do not help CPU-bound code); profiling is asking the program where it spends time instead of guessing; a package is a folder with a contract (`pyproject.toml`, tests, a README) that makes "it works on my machine" reproducible.

Topics in order: measuring — `time.perf_counter` vs `time.time`, `timeit` (`-n`, `-r`, why the min), `%timeit` in notebooks, `cProfile.run` and `pstats` sorted by cumulative time, reading a profile (tottime vs cumtime), `line_profiler` named, memory with `tracemalloc` and `sys.getsizeof` (a list of 10⁶ floats vs an array), benchmarking pitfalls (warm-up, caches, variance, `-O`); algorithmic complexity first — O(n²) pairwise forces vs O(n log n) tree methods (named: Barnes–Hut), the right data structure (PY-2 callback), early exit, caching (`lru_cache`, memoizing to disk with `np.save`/`np.load`, `pickle` and its security warning); constant factors — vectorize (PY-6), avoid Python-level loops over array elements, preallocate (`np.empty` + fill vs `append`), avoid repeated attribute lookups and function-call overhead in hot loops, in-place operations (`+=`, `out=`) to avoid temporaries, dtype choice (float32 halves memory and bandwidth — when acceptable), `np.einsum` and BLAS (`@` is already parallel), contiguity and cache (row-major access, `np.ascontiguousarray`), `scipy.spatial.cKDTree` for neighbor queries; the runtime — CPython's bytecode in one paragraph (`dis`), reference counting and the garbage collector, the GIL and what it does and does not block (I/O releases it; NumPy releases it inside many ufuncs), `threading` for I/O-bound, `multiprocessing`/`concurrent.futures.ProcessPoolExecutor` for CPU-bound (`map`, chunksize, pickling cost, the `__main__` guard, shared memory named), `asyncio` in one paragraph as "not for this"; compiling — Numba `@njit` (what it can compile, the first-call compile cost, `nopython` errors, `prange` with `parallel=True`), Cython and C extensions named, when to stop (good enough beats fastest); real software — project layout (`src/pkg/`, `tests/`, `pyproject.toml` with name/version/dependencies, `pip install -e .`), a CLI with `argparse` and an entry point, configuration (a dataclass loaded from JSON/TOML), reproducibility (seeds passed explicitly, `requirements.txt`/`pip freeze`, pinning, recording versions and the git commit in output files), logging over print (PY-5), docs (README with install/run/test, docstrings, `--help`), notebooks vs scripts (`# %%` cells as the curriculum's compromise; `jupytext`; the "restart and run all" rule), git — `init`, `status`, `add`, `commit`, `log`, `diff`, `branch`/`checkout`/`merge` in one small worked session, `.gitignore` (figures, data, caches), commit messages that say why, remotes in one paragraph; the checklist from Wilson et al. condensed.

Build-it-yourself sequences (the capstone spine): (1) the baseline — a pure-Python N-body step (N = 200) timed and profiled, with the profile read aloud ("90% in the force loop"); (2) vectorize the pairwise forces with broadcasting (PY-6 pairwise differences), softening added, asserted equal to the loop version to 1e-12, speedup measured; (3) remove temporaries with in-place ops and `out=`, measured (small gain — say so honestly); (4) float32 vs float64 timing and the energy-drift cost; (5) `ProcessPoolExecutor` over 8 initial conditions with the `__main__` guard, speedup vs core count measured (and the pickling overhead for small jobs shown as a *slowdown*); (6) Numba `@njit` on the loop version, first-call cost vs steady state, compared with vectorized NumPy (honest: often similar for this problem; Numba wins when the loop cannot be vectorized); (7) `cKDTree` to find neighbors within a radius for a short-range force, O(n log n) vs O(n²) scaling measured; (8) the package — `nbody/` with `pyproject.toml`, `src/nbody/{forces.py, integrate.py, cli.py}`, `tests/test_forces.py`, `pip install -e .`, `python -m nbody --n 100 --steps 500 --seed 1`; (9) a git session on the package: init, three commits with messages, a branch for an experiment, merge, `.gitignore` for `figures/`.

Worked examples (≥6): a `cProfile` output table for the baseline, annotated; the broadcasting force computation shape by shape; a speedup table (baseline, vectorized, in-place, float32, 4-process, Numba) with the measured numbers — these are measured by the writer's project.py run and must be reported as measured, with the hardware noted as "this container"; a `ProcessPoolExecutor` example where overhead loses; the `dis` output of `a + b` for three lines; a `pyproject.toml` with every field explained; the git session transcript.

§8 honest: everyone optimizes before profiling and speeds up the 5%; "Python is slow" is true per operation and irrelevant once the loop is in NumPy or Numba; threads will not speed up your CPU-bound code and you will try anyway; multiprocessing without the `__main__` guard spawns forever on some platforms; Numba error messages are terrible — start with tiny functions; float32 is a trade you must justify, not a free speedup; a package with `pyproject.toml` feels like ceremony for a 200-line simulation and is the difference between code you can reuse and code you rewrite; git's first week is miserable and then you cannot work without it; reproducibility means someone else can run it — if your seed is hard-coded inside a function, it is not reproducible, it is just deterministic.
