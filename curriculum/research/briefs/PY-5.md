§1 (the problem): a numerical routine that returns a plausible wrong number is worse than one that crashes — you will build a whole analysis on it. The forcing problem: your Simpson integrator from a previous exercise has an off-by-one in the odd/even panel handling that produces answers off by 0.3% that look fine; nothing in Python will tell you. You need a way for code to announce its own failure (exceptions), a way to pin down what it must do (tests), a way to see what it is doing (debugger, logging), and a way to catch wrong-type mistakes before running (type hints). §2 (the intuition): an exception is a signal that unwinds the call stack until something catches it — draw the stack with the exception climbing; a test is a small program whose only job is to fail loudly; a debugger pauses the program so you can look at the frames the traceback only names; a type hint is a comment the tools can check.

file open), exceptions for control flow (StopIteration) vs for errors, `assert` — what it is for (internal invariants) and what it is not (input validation; `python -O` removes them), `warnings.warn` and the categories, context managers — `with`, `__enter__`/`__exit__`, `contextlib.contextmanager` for a timer and a temporary directory; §8 honest: writing tests feels slow until the first time a test catches a bug you would have shipped — the integrator off-by-one is designed to be that time; `except Exception: pass` is how you turn a crash into a wrong answer; `assert` is removed by `-O`, so validating user input with it is a bug; people avoid pdb for years and lose hours to print statements — learn five commands; floating-point equality in tests needs `approx`, and the tolerance you pick is a claim about your algorithm, not a fudge; type hints do nothing at runtime and students expect them to; `pytest` not finding your tests is almost always a filename or function-name discovery rule.
